## Goal

pimd-rs evaluates a MACE model in-process, batched over beads, on CPU or GPU, so ML-RPMD runs without a socket round trip per bead. Validated against Python MACE on the same model, and against the M5 socket path with a Python MACE client. Then a small study: quantum effects on gas-phase water with MACE-OFF23, compared with the M5 GFN2-xTB results.

## Already done

M1–M5 merged; R1 on hold. Measured on this machine (2026-11-01):

## Decisions taken (owner, 2026-11-01)

1. M6 is split into spike, engine and study; the engine API is finalised after the spike.
2. Spike candidates: `tch` with a TorchScript export of the model, against the M5 socket path with a Python MACE client as baseline. ONNX (`ort`) is excluded (MACE's equivariant layers do not export cleanly); embedding Python (PyO3) only if `tch` fails.
3. The adapter supports float32 and float64 (D-1: f32 only inside model adapters). float64 is validated tightly, float32 to a looser stated tolerance. D-3 note: with the torch backend, bitwise guarantees hold only where the model evaluation is bitwise reproducible (expected: CPU with a fixed libtorch thread count; CUDA only if the spike shows deterministic algorithms work at acceptable cost); otherwise results, including restart, are checked to stated tolerances.
4. Build isolation: new crate `pimd-torch`; `pimd-cli` gains an optional feature `torch`; the default `check.sh` never needs libtorch; `CHECK_TORCH=1` runs the torch checks inside `pixi run -e ml`. New dependency `tch` (0.26) is approved by approving this brief.
5. Test models: a tiny randomly initialised MACE (a few kB, generated by a committed script with a fixed seed) for the fast tests; MACE-OFF23 only in long validation and the study, from an owner-supplied path (`PIMD_MACE_MODEL`).
6. Study: gas-phase water with MACE-OFF23 at 300 K, P convergence 1 … 32, quantum vs classical, comparison with M5 GFN2-xTB, throughput per bead on CPU and GPU; optionally one larger molecule (e.g. ethanol) for scaling. Numbers and plots, not a pass/fail gate.

## M6a: spike

Plan first (`docs/experiments/m6-spike.md`, written before running anything): the questions below, how each is measured, and what counts as success or failure. Then a log appended as work proceeds (commands, seeds, versions, outcomes, failures included), and a short writeup ending in a recommendation.

Code: `spikes/m6-torch/`, its own Cargo project, **not** a workspace member and not depended on by any crate; Python helpers next to it (run with `pixi run -e ml`). It is committed as the record of the spike and is not maintained afterwards. Nothing under `crates/` changes in M6a.

Models: the tiny random MACE (`gen_tiny_mace.py`, fixed seed; it later moves into `crates/pimd-torch/tests/data/` in M6b) and MACE-OFF23 small and medium (owner-supplied).

Questions:

1. **Build and run.** Does `tch` 0.26 build and link against the `ml` environment's libtorch, CPU and CUDA? How is the runtime library path set (rpath, `LD_LIBRARY_PATH`), does a built binary run outside `pixi run`, and what does it cost in build time and binary size?
2. **Export.** How is a MACE model exported to TorchScript (`torch.jit.script`, or mace's own export used for LAMMPS), with which input dictionary (positions, edge index, shifts, cell, node attributes, batch, ptr …) and outputs (energy; forces by autograd inside the model, and whether stress/virial is available)? Record the exact procedure so it can be scripted.
3. **Correctness.** Energies and forces from Rust (`tch`, TorchScript) vs Python MACE on the same model and geometry: water and one larger molecule, float64 and float32, CPU and CUDA. Report the max relative differences.
4. **Graph.** Edges built in Rust (all pairs within the model cutoff; gas phase, and orthorhombic minimum image with shift vectors) vs MACE's own neighbour list: same edge set, same results.
5. **Batching.** All P beads as one batched graph vs P separate calls: time per evaluation for P = 1, 8, 32 (water; the larger molecule), CPU at 1 and 4 libtorch threads, CUDA; float32 and float64.
6. **Determinism.** Repeated identical calls bitwise equal? CPU at a fixed thread count, CPU across thread counts, CUDA with and without `use_deterministic_algorithms(true)` (does it run, and at what cost)?
7. **Baseline.** The same water PIMD step through the M5 socket backend with a Python MACE client (four clients, as in M5): time per step, and agreement with question 3.

Time box: one working session of agent time. If `tch` does not build or link within it, stop and report with the error output rather than switching approach.

Writeup and recommendation, for the owner: backend; default dtype and device; batching; the determinism statement (exact D-3 note text); the edge-building approach; the export script; and a proposed final M6b section (signatures, rule P-6 text, config keys, tests, `CHECK_TORCH` mechanics). The owner decides; SPEC §12's open question is then closed.

## M6b: engine (tentative; finalised after the spike)

Expected shape, assuming `tch` and a TorchScript MACE model:

```rust
// pimd_torch (new crate; feature-gated build, needs libtorch)
pub enum Device { Cpu, Cuda(usize) }
pub enum Dtype { F32, F64 }

pub struct MacePotential { /* module, species, cutoff, device, dtype */ }
impl MacePotential {
    /// Loads a TorchScript MACE model; `atomic_numbers` has length N.
    pub fn load(path: &std::path::Path, atomic_numbers: &[u8], device: Device, dtype: Dtype)
        -> Result<MacePotential, PotentialError>;
}
impl Potential for MacePotential { /* all P beads in one batched call; eV, Å inside, Eh, bohr outside (U-3) */ }
```

Config (tentative):

```toml
[system]
symbols = ["O", "H", "H"]          # required for kind = "mace" (atomic numbers)

[potential]
kind = "mace"
model = "/path/to/model.pt"        # TorchScript export
device = "cpu"                     # or "cuda", "cuda:0"
dtype = "float64"                  # or "float32"
```

To settle in the amendment: what the config hash covers (dtype and device change results; the model file is identified by a hash of its bytes, not its path); unit conversion only through `pimd_core::units` (U-3; `HARTREE_IN_EV` and `BOHR_IN_ANGSTROM` exist); the symbol-to-atomic-number table lives in `pimd-torch`, not in the core crates; errors (`PotentialError::Backend` for torch failures, `ShapeMismatch` and `Unsupported` as P-1, P-4); the virial (P-5) only if the model provides it; how `verify_reference_data.py` runs a generator that needs the `ml` environment.

Required tests (tentative):

- Per evaluation vs Python MACE on the tiny model: energies and forces, float64 to a tight tolerance and float32 to a stated looser one; reference JSON from `crates/pimd-torch/tests/data/gen_*.py` (locked with the tests).
- Batched evaluation equals per-bead evaluation; bead independence; units (eV/Å inside, Eh/bohr out) with hand-converted values.
- Shapes, `subset = Some` → `Unsupported`, wrong atom count → `ShapeMismatch`, unknown symbol, missing or invalid model file.
- Determinism per the final D-3 note; restart K + checkpoint + K vs 2K (bitwise where D-3 promises it, otherwise to a stated tolerance).
- Config: new keys, validation, hash coverage.
- Long (`CHECK_LONG=1 CHECK_TORCH=1`, needs `PIMD_MACE_MODEL`): MACE-OFF23 water PIMD in-process vs the socket path with a Python MACE client, per evaluation and over a short trajectory, as the M5 bridge.

Mutant ideas: eV/Å conversion missing or inverted; forces taken as the gradient (sign); beads mixed up in the batch (ptr/batch offsets); edge shifts with the wrong sign; float32 cast applied to the outputs instead of inside the model; cutoff in bohr instead of Å; species order wrong.
